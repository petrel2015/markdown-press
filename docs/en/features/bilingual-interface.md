# Bilingual Interface

## Summary

The entire UI — labels, ARIA strings, page title, error notices and the
first-run sample document — exists in English and 简体中文, with
browser-language detection, a manual switch, and persistence.

## Background

Markdown's center of gravity is English, but a large share of this tool's
audience writes Chinese; CJK text also changes word-count semantics. A
bilingual UI from first paint — not machine-translated help text — was a
founding requirement.

## Problem

1. First visit must land in the user's language without a settings hunt.
2. The switch must re-label everything instantly — including ARIA labels
   and the `<title>` — without reloading or re-rendering the document.
3. Notices (export failed, file rejected, boot error) are generated by
   non-UI modules, so string lookup must be available everywhere, not just
   in static markup.
4. The sample document shown on first run should teach the editor in the
   user's language, including a Chinese-language quote where English would
   feel pasted-in.

## Goals

- Detect language from saved choice → browser languages → English.
- One dictionary per language; every user-visible string comes from it.
- Switch applies with zero flicker and no document re-render.
- Language choice persists and wins over detection on later visits.
- CJK-aware word counting in the status bar (each CJK character = 1 word).

## Non-Goals

- No more than two languages — dictionaries are hand-maintained; adding a
  third is a deliberate future decision, not a gap.
- No per-locale date/number formatting beyond the fixed status-bar shapes.
- No translation of *user content* — only chrome and the sample document.
- No right-to-left layout support.
- No region variants (en-GB, zh-TW); tags matching `zh*` → zh, `en*` → en.

## Solution Overview

`MD.i18n` holds both dictionaries in one structure and exposes `t(key,
params)` with `{n}`-style interpolation. Static markup declares
`data-i18n`, `data-i18n-aria-label` attributes; `apply()` walks them and
also rewrites `<title>` and `<html lang>`. Dynamic strings call `t()` at
render time (status bar, notices, mermaid error label, sample document).
Detection order: `localStorage['mdpress-lang']` if valid → first browser
language matching `zh*` or `en*` → `en`. The masthead switch calls
`setLang`, which persists and notifies listeners (app re-paints pressed
states, stats and save label).

## Detailed Behavior

- Unknown keys fall back to the English dictionary, then to the key itself.
- The language buttons set `aria-pressed` to reflect the current language.
- The sample document is served from the active dictionary — switching
  language does *not* replace the user's current document; it only changes
  what first-run would show.
- Storage failures (private mode) degrade to in-memory language choice.
- `html lang` becomes `zh-CN` or `en`, aiding screen readers and spellcheck
  suppression in the editor (`spellcheck=false` regardless).

## User Experience

The EN / 中文 pair sits in the masthead, top right. One click flips every
label; the red-underline active marker moves; the page title and status bar
follow. No reload, no lost cursor position.

## Compatibility and Historical Impact

Shipped with the initial release. No historical behavior is affected —
language handling has been dictionary-based from the first commit.

## Data and Privacy Impact

One `localStorage` key: `mdpress-lang` (values `en` or `zh`). No network,
no new permissions.

## Performance Impact

Dictionary lookups are plain object reads; `apply()` is a single
`querySelectorAll` pass over attributed elements on switch. Negligible; no
measurements published.

## Current Limitations

- Machine-translation quality risk is managed by hand-maintaining both
  dictionaries; they can drift if new strings are added to only one.
- The `prompt()`/`confirm()` dialogs use translated message text, but the
  browser-supplied buttons (OK/Cancel) render in the browser's language,
  not the app's.
